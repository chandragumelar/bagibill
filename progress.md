## Temuan F4-03 — paparan slug dan token klaim di log hosting Cloudflare

Ini LAPORAN, bukan perbaikan — di luar wewenang PR ini, keputusan arsitektur (kalau ada) punya konsekuensi ke bentuk URL yang cuma boleh diputuskan user. Ditulis sebagai bagian sendiri, bukan Catatan lepas, karena instruksi tugas eksplisit bilang ini mungkin temuan paling penting.

Slug di pesan error aplikasi sendiri sudah dibereskan (F4-01b, `settlement-repository.ts`). Ini soal beda: slug dan token ADA di path URL, dan path URL itu yang diproses lapisan edge Cloudflare di depan Pages buat routing setiap request — itu bukan sesuatu yang app-nya sendiri kirim sengaja, itu cara kerja HTTP.

**1. Apa yang beneran kecatat Cloudflare buat path request, dan bisa dimatikan?**

Dikonfirmasi lewat dokumentasi resmi Cloudflare (bukan tebakan): dataset "HTTP Requests" Cloudflare (buat Logpush, ekspor log request per-permintaan) punya field `ClientRequestURI` (path + query string lengkap) dan `ClientRequestPath` (path doang). Ini log request Cloudflare sendiri, di lapisan edge — bukan sesuatu yang app BagiBill kirim. Akses EKSPOR log ini (Logpush) dikonfirmasi cuma tersedia plan Enterprise (tabel resmi: Free/Pro/Business = tidak tersedia, Enterprise = tersedia).

Yang TIDAK bisa dipastikan dari dokumentasi publik, jadi ditulis apa adanya sebagai nol yakin, bukan ditebak: apakah tab Analytics bawaan Pages (yang kelihatan gratis di dashboard) memecah data per-path atau cuma agregat (jumlah request/bandwidth total), dan berapa lama Cloudflare internal menyimpan request log mentah di plan Free/gratisan (di luar yang bisa diekspor). Dua halaman dokumentasi yang coba dicek soal ini 404 pas diambil. **Cek langsung di dashboard Cloudflare pas proyeknya sudah jalan** — kalau tab Analytics ternyata nampilin daftar path per-request, itu temuan baru yang perlu masuk sini.

Soal "bisa dimatikan dari sisi konfigurasi": TIDAK ada toggle yang ketemu buat itu. Ini bukan fitur yang bisa di-opt-out — CDN/reverse proxy manapun (Cloudflare termasuk) secara struktural HARUS memproses path lengkap buat tahu ke mana routing request itu, dan sistem keamanan/anti-abuse mereka wajar melihatnya juga. Nol ada provider hosting yang menawarkan "jangan lihat path saya" sebagai pengaturan, karena itu bertentangan dengan cara HTTP bekerja.

**2. Token klaim `/c/:token` — paparan sama atau lebih buruk dari slug?**

MEKANISME-nya sama persis: keduanya sama-sama string di path URL, lewat lapisan edge yang sama, dengan visibilitas yang sama ke Cloudflare. Nol ada beda teknis antara `/g/:slug` dan `/c/:token` di titik ini.

KONSEKUENSI-nya lebih buruk buat token. Slug (per CLAUDE.md) "semi-rahasia" — cukup susah ditebak tapi bukan kunci akses tunggal. Token klaim itu bearer-token: siapapun yang pegang string itu bisa klaim/lihat isi pengeluaran, tanpa autentikasi tambahan. Kalau ada pihak (staf Cloudflare, atau kalau proyek ini suatu saat naik ke Enterprise dan seseorang lupa itu ada log Logpush yang nyala) yang bisa lihat log path, mereka dapat token itu utuh — bukan cuma "tahu ada grup bernama X", tapi "bisa langsung buka linknya sendiri". `Referrer-Policy: no-referrer` (K-152) nutup jalur kebocoran yang beda (link keluar dari halaman ke pihak ketiga), nol menyentuh jalur ini sama sekali.

**3. Bisa dihilangkan tanpa mindahin slug/token ke fragment (`#`)?**

TIDAK. Terang-terangan: TIDAK BISA. Ini bukan soal konfigurasi Cloudflare yang kurang pas — fragment URL (bagian setelah `#`) itu SATU-SATUNYA bagian URL yang menurut spesifikasi (RFC 3986) nol pernah dikirim ke server sama sekali, murni ditangani browser. Selama slug/token ada di PATH (bagian sebelum `#`), mereka struktural terlihat oleh setiap lapisan yang memproses request — Cloudflare edge, log apapun yang mereka simpan, cache jaringan di antara, dsb. Nol ada header atau pengaturan `_headers`/CSP yang bisa menutup ini, karena masalahnya ada di tahap SEBELUM app-nya sendiri kebuka.

**PERTANYAAN terbuka buat user** (bukan diputuskan di PR ini): apakah exposure ini cukup penting buat suatu saat memindahkan slug/token ke fragment URL? Itu ubah bentuk link yang dibagikan (kurang lazim buat orang awam, potensial masalah kalau ada server-side rendering/share preview yang baca path), jadi trade-off yang lebih besar dari sekadar konfigurasi header. Nol ada perubahan routing dikerjakan di PR ini sesuai batas tugas.
